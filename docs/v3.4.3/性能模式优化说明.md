# v3.4.3 性能模式优化说明

## 已完成优化

进入托盘性能模式时的清理动作：

- **KeepAlive 组件缓存释放**（`keepAliveKey++`）：销毁最多 20 个路由组件实例
- **DOM 树卸载**（`v-if`）：隐藏主窗口、播放控制条、播放列表、全屏播放器
- **Blob URL 清理**：释放封面缓存（保留当前及下一首）
- **歌词缓存清理**：仅保留当前及下一首
- **Store 数据清理**：释放 dataStore、localStore 中的非必要缓存
- **歌词偏移记录修剪**：只保留最近 50 条
- **AudioSource / Analysis 缓存清理**：PlayerController + AutomixManager
- **背景图片 Blob URL 释放**
- **抖音收藏数据清理**
- **V8 GC 主动触发**（`window.gc()`，配合 `--expose-gc` 标志）

## 实测数据

| 指标 | 数值 |
|---|---|
| 任务管理器总内存 | ~780MB |
| JS 堆（V8 管理） | ~65MB（8%） |
| 其余（Electron/Chromium 内核） | ~715MB（92%） |

## 为什么再也无法大幅优化

### JS 堆已见底

65MB 的 JS 堆是播放器正常运行的底线，包含了 Vue 响应式数据、播放状态、歌词数据、播放列表等核心运行时对象。已无可清理空间。

### Electron 内核内存是死开销

715MB 分布于以下不可减撤的层级：

| 层级 | 约占用 | 为什么不能减 |
|---|---|---|
| Chromium 渲染引擎 | 200-300MB | 界面渲染基础，无它无法显示任何 UI |
| GPU / Skia 管线 | 100-150MB | 动画、模糊、封面绘制的基础设施 |
| V8 引擎本体 | 80-100MB | JS 代码执行的虚拟机 |
| Node.js 运行时 | 20-40MB | 文件系统、网络、进程管理等核心能力 |
| **better-sqlite3** | 30-50MB | 歌曲缓存、收藏数据持久化 |
| **sharp** | 30-50MB | 封面图片处理、格式转换 |
| **FFmpeg** | 20-40MB | 音频解码支持 |
| **Web Audio Context** | 60-80MB | 主播放管线，性能模式下仍需运行 |
| 网络栈 | 30-50MB | HTTP/2、WebSocket、DNS |

### 渲染进程无法销毁

音频播放、桌面歌词、任务栏歌词、Store 状态全部在渲染进程中运行。关闭它 = 应用停止，不是"优化"而是"退出"。

### 换框架同样省不掉

切换到 Tauri/Flutter 等轻量框架，仍然需要：
- 浏览器内核或 GPU 渲染引擎
- 音频解码与处理
- 数据库、图像处理、网络栈

预计最终内存 250-400MB，换来的代价是**全部代码重写**（JS 复用率约 30%），投入 6-12 个月全职开发。

---

## 结论

当前性能模式已实现了**所有能做的 JS 层优化**。780MB 是功能完整的 Electron 音乐播放器的正常水平，与同类产品（Apple Music 桌面版、QQ 音乐桌面版）相当。继续深挖的投入产出比不合理。
